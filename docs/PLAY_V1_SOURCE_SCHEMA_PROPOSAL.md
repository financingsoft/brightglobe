# Globe Play — V1 Transactional Source Schema Proposal

**Status:** Proposed logical contract · Draft only · Requires review  
**Depends on:** PLAY_MARKETPLACE_MASTER_CONTRACT.md, PLAY_MARKETPLACE_DATA_CONTRACT.md, PLAY_DATA_MODEL_V2_CONTRACT.md, PLAY_DOMAIN_ARCHITECTURE_CONTRACT.md, PLAY_SECURITY_TRUST_CONTRACT.md, PLAY_PROJECTION_PIPELINE_CONTRACT.md and PLAY_STAGING_DATABASE_AUDIT.md  
**Database target:** Neon `neondb`, isolated `marketplace` schema  
**Migration status:** No DDL is authorized or included in this proposal.

## 1. Purpose and boundary

This document turns the existing logical marketplace model into a coherent V1 transactional source-of-truth proposal. It is deliberately a design contract, not executable SQL. The purpose is to settle table ownership, state transitions, identity references, immutable publication snapshots and transaction boundaries before writing a migration or Neon adapter.

The existing public-read architecture remains unchanged:
- `globe-play` public read routes read only sanitized projection tables.
- Transactional Marketplace services write source records and outbox events.
- A separate relay publishes outbox event IDs to Cloudflare Queues.
- A separate projector consumes events, updates public projections and performs targeted cache invalidation.
- Payload CMS remains editorial-only; it cannot own app, developer, review, artifact or release approval state.

No source table, role, Queue, migration, secret or Worker is created by this proposal.

## 2. Decisions required to resolve existing contract overlap

The current Data Contract and Data Model V2 contain overlapping representations. The following are explicit proposed resolutions, not silent implementation changes:

| Existing overlap | Proposed V1 resolution | Reason |
|---|---|---|
| `apps` stores name, description, locale and publication fields directly; V2 adds immutable listing revisions/localizations | `apps` stores stable identity, ownership, slug and lifecycle/version pointers; editable/public metadata lives in immutable `app_listing_revisions` and child revision tables | Review must approve an exact snapshot; editing a draft must never mutate already-published content |
| Developer owner field plus membership roles | Memberships are the authorization source of truth; exactly one active `owner` membership per developer | Avoid two competing ownership authorities |
| Initial roles owner/maintainer/analyst vs V2 roles | Use `owner`, `admin`, `release_manager`, `analyst`, `support_readonly` | One consistent tenant role vocabulary |
| `platforms` attached directly to app vs V2 platform targets | Use revision-scoped `app_listing_platform_targets` for displayed compatibility; releases/artifacts remain separate | Compatibility is part of the reviewed listing snapshot |
| App version and distribution source mixed together | Separate `app_versions`, immutable `app_artifacts`, `distribution_sources`, `releases` | Package provenance, release approval and public distribution eligibility are different facts |
| Review body directly mutable plus revisions | `reviews` is the current review aggregate; each edit appends immutable `review_revisions` | Preserve history and make moderation decisions attributable |
| Generic audit and outbox | Separate append-only `audit_events` from delivery-oriented `domain_outbox` | Audit retention and event retry have different access and lifecycle requirements |

These decisions need to be reflected in the binding Data Contract before implementation. If any existing contract owner rejects a resolution, stop and amend the design before DDL.

## 3. Identity and tenant rules

### Canonical identity

Every user reference uses `public.canonical_users(id)` (UUID). Never reference Better Auth `public."user".id` from Marketplace business tables. Resolve Better Auth/wallet identity through the existing BrightGlobe identity layer before calling Marketplace services.

Every Marketplace-owned UUID is generated by the application using UUIDv7. The schema must not assume a database extension for UUIDv7 generation unless the existing platform contract explicitly adds one.

### Developer organization

A developer organization is the tenant boundary. A user can belong to multiple organizations; an organization can have multiple users.

Membership role is the sole authorization authority:
- `owner`: organization ownership and all tenant actions.
- `admin`: manage members and app metadata, but cannot transfer ownership or override platform review.
- `release_manager`: submit/manage releases and artifacts within policy.
- `analyst`: read tenant analytics only.
- `support_readonly`: read approved support context only.

Required invariants:
1. Every active developer organization has exactly one active owner membership.
2. Membership role changes and owner transfer are atomic and audited.
3. No client-supplied developer ID grants access; every query is scoped by server-resolved canonical user and active membership.
4. Platform staff roles are separate from tenant membership roles.
5. A developer cannot approve its own verification, app listing, artifact scan or release.

## 4. V1 source-of-truth table inventory

All tables below live in `marketplace`. The list is intentionally limited to the first complete publish-and-review loop. Upload scanning, staged rollout, notifications, analytics and appeals can be added in subsequent additive migrations after the core invariants are tested.

### 4.1 Tenant and authorization

#### `developers`
Stable publisher organization identity:
- `id uuid PK`
- `slug varchar(100) UNIQUE NOT NULL`
- `display_name varchar(120) NOT NULL`
- `description text NULL`
- `website_url text NULL`
- `support_email text NULL` (private unless explicitly opted into public listing)
- `verification_status` (unverified, pending, verified, rejected, suspended)
- `status` (pending, active, suspended, closed)
- `created_by_canonical_user_id uuid FK canonical_users`
- `aggregate_version bigint NOT NULL`
- `created_at, updated_at timestamptz NOT NULL`

The creator is attribution, not the ownership authority. Do not duplicate an owner ID here.

#### `developer_memberships`
- `developer_id uuid FK developers`
- `canonical_user_id uuid FK canonical_users`
- `role` (owner, admin, release_manager, analyst, support_readonly)
- `status` (invited, active, suspended, revoked)
- `created_at, updated_at timestamptz NOT NULL`
- `created_by_canonical_user_id uuid FK canonical_users`
- composite primary key `(developer_id, canonical_user_id)`

Use a partial unique index to enforce at most one active owner per developer; the owner-transfer service transaction must ensure the resulting organization has exactly one. An organization cannot be activated without an owner. Membership invitation tokens are stored hashed in a separate `developer_invitations` table when invitation workflows are implemented.

### 4.2 App identity and immutable listing revisions

#### `apps`
Stable app identity and lifecycle:
- `id uuid PK`
- `developer_id uuid FK developers`
- `slug varchar(140) UNIQUE NOT NULL`
- `app_type` (app, game)
- `status` (draft, submitted, in_review, published, rejected, suspended, archived)
- `current_draft_revision_id uuid NULL`
- `current_published_revision_id uuid NULL`
- `aggregate_version bigint NOT NULL`
- `created_by_canonical_user_id uuid FK canonical_users`
- `created_at, updated_at, published_at timestamptz NULL`

The app row is not the editable listing body. Its stable slug is not changed by ordinary copy edits. Slug changes require a separate audited operation, redirect policy and cache invalidation.

#### `app_listing_revisions`
Immutable submission snapshots:
- `id uuid PK`
- `app_id uuid FK apps`
- `revision_number integer NOT NULL`
- `content_locale varchar(16) NOT NULL`
- `name varchar(160) NOT NULL`
- `tagline varchar(240) NULL`
- `description text NOT NULL`
- `website_url, privacy_policy_url, support_url text NULL`
- `content_rating varchar(32) NULL`
- `privacy_disclosure jsonb NOT NULL DEFAULT '{}'`
- `metadata_checksum char(64) NOT NULL`
- `status` (draft, submitted, in_review, approved, rejected, superseded)
- `submitted_by_canonical_user_id uuid FK canonical_users NULL`
- `reviewed_by_canonical_user_id uuid FK canonical_users NULL`
- `decision_code varchar(40) NULL`
- `decision_note text NULL` (private)
- `submitted_at, reviewed_at, created_at timestamptz NULL/NOT NULL`

Unique `(app_id, revision_number)`. Once submitted, listing content and child relations are immutable. A change creates a new revision. Reviewer decisions are append-only in a separate decision history table or audit event; do not overwrite a prior decision without preserving it.

#### `app_listing_revision_categories`
- `revision_id uuid FK app_listing_revisions`
- `category_id uuid FK categories`
- composite primary key `(revision_id, category_id)`

#### `app_listing_revision_media`
- `id uuid PK`
- `revision_id uuid FK app_listing_revisions`
- `media_type` (icon, screenshot, video, banner)
- `approved_object_version_id uuid NULL` (reference to an approved media asset record; never raw private/quarantine key in public projection)
- `alt_text varchar(240) NOT NULL`
- `sort_order integer NOT NULL`

#### `app_listing_platform_targets`
- `id uuid PK`
- `revision_id uuid FK app_listing_revisions`
- `platform` (android, ios, web, windows, macos, linux)
- `architecture varchar(64) NULL`
- `minimum_os_version varchar(64) NULL`
- `maximum_os_version varchar(64) NULL`
- `availability_status` (available, planned, unavailable, region_limited)
- `region_allowlist jsonb NULL`
- unique normalized target key per revision

A listing revision is publishable only when its category, media, platform and disclosure checks all pass.

#### `categories`
Platform-governed taxonomy:
- `id uuid PK`
- `slug varchar(80) UNIQUE NOT NULL`
- `parent_id uuid NULL FK categories`
- `status` (active, hidden, retired)
- `sort_order integer NOT NULL`
- localized labels/descriptions should live in a separate `category_localizations` table before multiple locale labels are published.

### 4.3 Version, artifact and distribution

#### `app_versions`
Logical publisher release version:
- `id uuid PK`
- `app_id uuid FK apps`
- `platform varchar(24) NOT NULL`
- `version_name varchar(80) NOT NULL`
- `version_code varchar(80) NULL`
- `release_notes text NULL`
- `status` (draft, submitted, scanning, approved, rejected, withdrawn)
- `created_by_canonical_user_id uuid FK canonical_users`
- `created_at, updated_at timestamptz NOT NULL`
- unique `(app_id, platform, version_name)`

#### `app_artifacts`
Immutable binary provenance record:
- `id uuid PK`
- `app_version_id uuid FK app_versions`
- `storage_object_version_id uuid NOT NULL` (opaque internal object reference; not public URL)
- `sha256 char(64) NOT NULL`
- `size_bytes bigint NOT NULL`
- `detected_mime varchar(120) NOT NULL`
- `package_identifier varchar(255) NULL`
- `bundle_identifier varchar(255) NULL`
- `signer_fingerprint varchar(255) NULL`
- `provenance jsonb NOT NULL`
- `scan_status` (pending, clean, suspicious, malicious, error)
- `approval_status` (pending, approved, rejected, revoked)
- `created_at timestamptz NOT NULL`

Artifact object identity and hash are immutable. A changed binary is a new artifact row. Raw R2 keys and private object metadata never appear in public projections.

#### `distribution_sources`
Approved route to an app version:
- `id uuid PK`
- `app_version_id uuid FK app_versions`
- `source_type` (official_store_link, developer_download, globe_hosted_verified, test_distribution)
- `source_url text NULL` (validated HTTPS only; never expose unvalidated redirect target)
- `artifact_id uuid NULL FK app_artifacts`
- `verification_status` (pending, verified, rejected, revoked)
- `status` (pending, active, withdrawn)
- `region_policy jsonb NOT NULL DEFAULT '{}'`
- `approved_by_canonical_user_id uuid FK canonical_users NULL`
- `approved_at timestamptz NULL`
- `created_at, updated_at timestamptz NOT NULL`

A public distribution source is eligible only when its version, source, artifact (when hosted), scan and approval state all pass. Download authorization always checks current transactional state; cached metadata is not an authorization grant.

### 4.4 Reviews, revisions, votes and moderation

#### `reviews`
Current review aggregate:
- `id uuid PK`
- `app_id uuid FK apps`
- `canonical_user_id uuid FK canonical_users`
- `rating smallint NULL` (1–5 when present; text-only reviews allowed)
- `status` (pending, published, rejected, hidden, removed)
- `publisher_affiliation` (none, employee, contractor, other)
- `current_revision_id uuid NULL`
- `aggregate_version bigint NOT NULL`
- `created_at, updated_at timestamptz NOT NULL`
- `published_at timestamptz NULL`

A partial unique constraint enforces at most one active review per canonical user/app (the precise statuses included must be tested). Rating is optional and must never be inferred from sentiment. Rating aggregates include only currently published eligible ratings and are precomputed.

#### `review_revisions`
- `id uuid PK`
- `review_id uuid FK reviews`
- `revision_number integer NOT NULL`
- `title varchar(160) NULL`
- `body text NOT NULL`
- `experience_context jsonb NOT NULL DEFAULT '{}'` (strictly minimized)
- `change_reason text NULL`
- `created_by_canonical_user_id uuid FK canonical_users`
- `created_at timestamptz NOT NULL`
- unique `(review_id, revision_number)`

#### `review_votes`
- `review_id uuid FK reviews`
- `canonical_user_id uuid FK canonical_users`
- `vote` (helpful, not_helpful)
- `created_at, updated_at timestamptz NOT NULL`
- composite primary key `(review_id, canonical_user_id)`

#### `moderation_cases`
- `id uuid PK`
- `target_type`, `target_id`
- `reporter_canonical_user_id uuid FK canonical_users NULL`
- `assigned_to_canonical_user_id uuid FK canonical_users NULL`
- `reason_code varchar(40)`
- `status` (open, investigating, actioned, dismissed, appealed)
- `resolution_code varchar(40) NULL`
- `created_at, updated_at timestamptz NOT NULL`

Private evidence is stored outside public projection payloads with restricted access and retention. Moderation decisions are audited and must not be overwritten by publisher actions.

### 4.5 Audit and transactional event delivery

#### `audit_events`
Append-only record for security, ownership, submission, review, moderation, artifact and release decisions:
- `id uuid PK`
- `actor_canonical_user_id uuid NULL FK canonical_users`
- `actor_type` (user, platform_operator, system)
- `action varchar(80)`
- `target_type varchar(40)`
- `target_id uuid`
- `reason_code varchar(40) NULL`
- `correlation_id varchar(100) NOT NULL`
- `metadata jsonb NOT NULL DEFAULT '{}'`
- `created_at timestamptz NOT NULL`

No secrets, auth tokens, private evidence or unnecessary personal data in metadata. Runtime DB role should have INSERT but not UPDATE/DELETE; privileged retention/maintenance is separate and audited.

#### `domain_outbox`
Written in the same transaction as every mutation that changes a public representation:
- `event_id uuid PK` (UUIDv7)
- `event_type varchar(80) NOT NULL`
- `schema_version integer NOT NULL`
- `aggregate_type varchar(40) NOT NULL`
- `aggregate_id uuid NOT NULL`
- `aggregate_version bigint NOT NULL`
- `payload jsonb NOT NULL` (sanitized public snapshot or tombstone only)
- `invalidation_tags text[] NOT NULL`
- `occurred_at timestamptz NOT NULL`
- `available_at timestamptz NOT NULL`
- `lease_owner varchar(120) NULL`
- `lease_expires_at timestamptz NULL`
- `attempt_count integer NOT NULL DEFAULT 0`
- `last_error_code varchar(80) NULL`
- `dispatched_at timestamptz NULL`
- `created_at timestamptz NOT NULL`

Indexes: pending dispatch partial index by `available_at, created_at`; aggregate history index by `aggregate_type, aggregate_id, aggregate_version`; uniqueness on `(aggregate_type, aggregate_id, aggregate_version, event_type)` only if event semantics guarantee one such event per version. Otherwise event ID is the sole idempotency key.

Outbox payload must not contain canonical user IDs, email, private moderation evidence, private R2 object keys, scanner internals, secrets, internal notes or unapproved URLs.

#### `projection_event_receipts`
Durable projector receipt:
- `event_id uuid PK`
- `aggregate_type varchar(40) NOT NULL`
- `aggregate_id uuid NOT NULL`
- `aggregate_version bigint NOT NULL`
- `outcome` (applied, stale, deleted, ignored)
- `invalidation_state` (pending, completed, not_required)
- `applied_at timestamptz NOT NULL`
- `invalidation_completed_at timestamptz NULL`

A unique event receipt and projection mutation commit atomically. A receipt with pending invalidation must be retryable after duplicate Queue delivery. Do not mark invalidation complete until every purge chunk is accepted.

#### `projection_aggregate_watermarks`
- `aggregate_type varchar(40)`
- `aggregate_id uuid`
- `latest_version bigint NOT NULL`
- `deleted_at timestamptz NULL`
- `updated_at timestamptz NOT NULL`
- composite primary key `(aggregate_type, aggregate_id)`

This watermark/tombstone survives projection row deletion. It prevents delayed older upserts from resurrecting deleted content. Watermark updates, projection changes and event receipts are atomic.

## 5. Transactional invariants and state transitions

### App submission and publication

1. Developer creates/edits a draft revision. Submitted revisions are immutable.
2. Submission transaction verifies active membership and object ownership, locks app aggregate, increments app aggregate version, marks exact revision submitted, appends audit event and (if public state changes) writes the corresponding outbox event.
3. Reviewer decision is a separate privileged transaction with reviewer authorization, reason code, immutable decision/audit record and aggregate version increment.
4. Approval alone does not publish. Publication requires an explicit publish transition after all listing/media/platform/privacy checks pass.
5. Publication transaction sets the approved revision pointer, changes app status, builds a sanitized projection snapshot from that exact revision and approved distribution data, inserts outbox event and audit record, all in one transaction.
6. Editing a later draft cannot mutate the published revision or public projection until a new revision is reviewed and published.

### Review lifecycle

1. A review is created as pending and receives an immutable first revision.
2. Moderator publication makes it eligible for the public projection; rating is optional and only explicit 1–5 values count.
3. User edits append a new revision and return to pending review; the currently published revision remains visible until policy explicitly withdraws it.
4. Hide/remove/reject changes eligibility and emits a delete/update projection event in the same transaction.
5. Rating summary is recomputed from eligible published ratings in the transaction or a versioned aggregate process; it is never computed by public read queries.

**Open policy requiring product decision:** whether edited review text remains visible while its new revision is pending, and whether at most one active review means one per app or one per app/version. Until resolved, do not encode this behavior in DDL/API.

### Outbox relay and projector

- Relay claims bounded rows using `FOR UPDATE SKIP LOCKED` and a short lease in a transaction.
- Queue send occurs outside the DB transaction; after successful send, relay marks the row dispatched. A crash between send and mark can duplicate delivery and is expected.
- Projector validates event ID/schema, loads immutable outbox data, then atomically checks watermark, applies projection/tombstone and inserts receipt.
- Cache purge happens after projection transaction commit. A purge failure leaves receipt pending; retry resumes purge idempotently.
- A stale event cannot update projection or watermark. A deletion tombstone is retained even when public projection rows are removed.
- Relay/projector retries are bounded; exhausted delivery goes to DLQ and requires alert/replay operations.

## 6. Role and permission separation

| Role | Minimum authority | Must not have |
|---|---|---|
| Marketplace API | Source-table operations needed for authorized domain services; append audit/outbox | Public projection writes unless a specific service contract requires it |
| Public reader | SELECT on approved public projection tables only | Source-table access, writes, purge secrets |
| Outbox relay | SELECT/lease/update dispatch metadata on outbox; Queue send secret | App/review mutation, projection write |
| Projector | Read immutable outbox; write projection, receipt and watermark tables; purge secret | User auth, app source mutation, moderation decisions |
| CMS | Editorial-owned schema/content only | App ownership, release/artifact approval, Marketplace source/outbox |
| Scanner callback | Append scan result for its assigned artifact/job | Release approval, source promotion, arbitrary app updates |
| Operations | Explicitly scoped audited intervention | Shared human credentials or unrestricted public-reader access |

Exact grants must be derived from concrete SQL statements and verified with role-level negative tests. Do not grant broad schema ownership to runtime roles.

## 7. Projection contracts and public data

Only approved published listing revisions and currently eligible public distribution sources can enter public projections. Projection payloads contain display-ready fields, safe public URLs, approved media URLs, published rating aggregates and public developer details.

Never project:
- canonical user IDs, emails, internal membership or account state;
- draft revisions, reviewer notes, moderation evidence or private reports;
- quarantine/private R2 keys, scanner logs or private package metadata;
- unapproved, withdrawn or region-ineligible distribution targets;
- private support email unless the publisher explicitly opts in;
- unverified publisher badges or fabricated ratings.

App projection keys are stable `(app_slug, content_locale)`. Review projection ordering is deterministic `created_at DESC, review_id DESC`; cursor pagination remains bounded and signed. Aggregate versions are monotonic.

## 8. Index, deletion and concurrency requirements

- Every FK used in join/delete paths receives a deliberate index; avoid duplicate indexes already provided by unique/PK constraints.
- Normalize nullable uniqueness dimensions before creating unique indexes.
- Use partial indexes for active memberships/reviews and pending outbox rows.
- Use explicit ON DELETE behavior; publisher, app, review and audit history must not disappear through accidental cascade.
- Prefer soft-state transitions for published/regulated content; hard deletion is a separately audited retention workflow.
- Lock aggregate roots or use compare-and-swap on `aggregate_version`; database constraints remain concurrency authority.
- Outbox and audit rows are retained according to separate documented policies; do not delete pending events during cleanup.
- Use deterministic page order and bounded page sizes.

## 9. Required tests before writing or applying a migration

### Schema and constraint tests
- UUIDv7 IDs and canonical identity FKs.
- Cross-tenant membership isolation and object authorization.
- Exactly one active owner; atomic owner transfer and failed last-owner removal.
- Unique slug, app revision number, app platform/build identity, active review policy and review vote.
- Immutable submitted/published revisions.
- No accidental cascade of audit, release or published history.
- Role grants: public reader cannot SELECT source or write; projector cannot mutate source; relay cannot mutate projections; CMS/scanner cannot approve releases.

### Transaction and event tests
- Source mutation + audit + outbox are all committed or all rolled back.
- Queue send success followed by relay crash causes safe duplicate delivery.
- Out-of-order event versions do not regress projection.
- Delete tombstone blocks delayed upsert resurrection.
- Duplicate event resumes pending cache invalidation.
- Partial multi-chunk purge failure retries safely.
- Review publish/edit/hide/remove updates rating and review projections consistently.
- Developer/category before-and-after tags cover relationship changes.
- A publisher cannot expose a draft, quarantined artifact or unapproved distribution source.

### Operational tests
- Migration applies to an isolated Neon branch and can be rolled forward safely.
- Direct (non-pooled) Neon connection is used for migrations; pooled connections remain for serverless app traffic.
- Staging migration requires separate explicit approval.
- Neon scale-to-zero cold-start and Cloudflare cache-hit behavior are measured; no claim of zero cost.
- Queue retry/DLQ, purge rate limiting, replay and operator audit are verified.

## 10. Decisions still required before DDL

1. Review uniqueness: one active review per app, or per app/version?
2. Edited review behavior while the new revision is pending.
3. Whether multiple locales are submitted/reviewed independently per app or as one grouped submission.
4. Whether app slug changes are allowed in V1 and exact redirect retention policy.
5. Which V1 artifact formats/platforms Globe may host versus link to official stores only.
6. Exact review rating aggregation policy and locale scope.
7. Category localization ownership and initial taxonomy.
8. Exact audit/outbox retention and hard-delete/legal-hold policy.
9. Exact membership invitation and owner-transfer approval rules.
10. Exact source-side DB role and API query grants after SQL implementation exists.

These are blockers for production DDL where they affect constraints or lifecycle. Do not invent defaults silently.

## 11. Explicit non-goals

- No SQL migration or schema execution.
- No Neon role/grant creation or database data writes.
- No Queue/DLQ provisioning or Cloudflare purge token.
- No Worker/API implementation or deployment.
- No DNS, R2 bucket/policy, CDN/cache or Production changes.
- No review rewards, BD/BG integration, payment processing or token functionality.
- No PR merge.

This proposal is ready for architecture review only. A subsequent implementation task may convert the approved subset into a Drizzle schema and draft additive migration, followed by isolated PostgreSQL/Neon branch tests.
