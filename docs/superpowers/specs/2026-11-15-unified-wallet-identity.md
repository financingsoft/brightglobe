# BrightGlobe Unified Identity Architecture

**Status:** Approved for implementation planning; Better Auth nullable-email gate failed and architecture was revised  \
**Date:** 2026-11-15

## Approved product and identity decisions

1. BrightGlobe has one canonical internal user identity. Every business record uses the same `canonicalUserId`.
2. `canonicalUserId` is generated by the backend as UUIDv7. Clients cannot choose or override it.
3. Every new email-first or wallet-first registration creates a canonical identity.
4. Email authentication continues to use Better Auth 1.7.23. Solana wallet authentication uses a separate BrightGlobe wallet-session mechanism.
5. Both authentication mechanisms resolve to the same canonical identity before business authorization. Business services must not use a Better Auth user ID as their user primary key.
6. Wallet-only registration does not require an email. Email is optional and may be added and verified later.
7. A user may bind multiple Solana wallets; a wallet address may belong to only one canonical user.
8. Linking identities requires proof of control of the identity being added and an authenticated session for the canonical account. Never merge accounts based only on matching claims or client-supplied identifiers.
9. The previous proposal to make Better Auth's `user.email` nullable and to use one Better Auth session system is superseded.

## Canonical identity and authentication mapping

- Add a BrightGlobe-owned canonical identity table with UUIDv7 primary key and lifecycle/audit timestamps.
- Add an authentication identity mapping table. It maps a provider identity (for example, Better Auth's existing `user.id` or a verified Solana wallet identity) to exactly one `canonicalUserId`.
- Keep Better Auth's own user/session/account/verification tables as the email-authentication subsystem. Its user ID is a provider-local identifier only, never the business user ID.
- Wallet-only users do not get synthetic Better Auth users or placeholder email addresses.
- Wallet sessions are independently issued, stored, expired, and revoked. A shared authentication middleware resolves either valid session type to a canonical identity and exposes only `canonicalUserId` to business routes.
- Session revocation, cookie scope, CSRF protections, origin checks, and session rotation must be explicitly tested for both mechanisms.
- The canonical identity table is the authority for account lifecycle. Provider records are authentication credentials, not business identities.

## Staging reset decision

The user explicitly chose a clean restart rather than migrating existing Better Auth users or historical user data.

- Do not migrate existing Better Auth user IDs, sessions, accounts, verification rows, or profile rows into the new canonical identity system.
- The existing Staging authentication records were reported as cleared. Before implementation applies migrations, independently verify the live Staging schema and row counts; do not infer database state from this document alone.
- Keep the empty Better Auth schema required for the existing email-authentication subsystem unless a separately reviewed migration proves a table can be removed safely.
- Do not truncate the entire database or delete non-authentication business tables as part of identity initialization.
- Existing BD ledger/business data is out of scope. Do not rename BD to BG, convert balances, or alter historical BD records.
- Existing users must register again after the new identity system is released. This is an intentional reset, not an account migration.

## Wallet proof requirements

- Use a server-generated, cryptographically random, single-use nonce.
- Challenge is short-lived and bound to expected domain/origin, URI, statement/action, Solana network, wallet address, and issued/expiry times.
- Verify the Ed25519 signature against the exact server-issued message.
- Consume the challenge atomically with the successful identity operation to prevent replay and concurrent reuse.
- Never request, transmit, or store wallet private keys or seed phrases.

## Security and data integrity invariants

- One provider identity maps to exactly one canonical user.
- A wallet address has one owner globally within the relevant network namespace.
- An authentication session resolves to one active canonical user; disabled/deleted canonical users cannot authenticate.
- Account linking must be transactional and resistant to races.
- Public authentication errors must not disclose whether an email or wallet is registered.
- Rate-limit challenge issuance, signature verification, email signup, and login attempts.
- Audit identity creation, linking, unlinking, session revocation, and administrative lifecycle changes without logging secrets or raw session tokens.

## Environment and release constraints

- Implement and verify locally and against Staging/Devnet only.
- Do not modify Production Worker `globe` or Production Neon.
- Do not enable Solana Mainnet, mint BG, initiate transfers, or enable rewards.
- Do not expose secrets in code, logs, tests, or documentation.
